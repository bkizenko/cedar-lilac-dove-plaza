# Visible village-file transfer and asynchronous ownership — 2026-11-02

Baseline b0c9557, isolated `.play/village-import-lifecycle-review`. Scope: Engine.importVillage, HUD transfer extraction, and a new VillageFileTransfer component. No save validator, schema, storage limit, backup requirement or production recipe is changed.

The observed root IAB chooser attempt did not visibly change the village. This artifact does **not** identify its cause. The existing HUD captures a File object before clearing the input, and inspection alone does not prove that clearing cancels File.text. The previous engine catches errors as short banners and returns no outcome; a user cannot distinguish pending read, rejected import, successfully applied state or a later local-save failure from persistent transfer UI.

The transfer disclosure now disables file selection until an engine exists and while the selected transfer is pending. It shows “Importing village…” and keeps the actual final message visible in a polite status line. A ref prevents duplicate same-tick UI submissions; the input clears only in finally, so the same file can be selected again after completion or failure. Component unmount/engine changes suppress stale state updates.

Engine import captures the actual Game object, its state object and a monotonically increasing import sequence before awaiting File.text. Disposal, actual reset/restart, a different active game, an active test session or a newer import invalidates that attempt before parsing, protecting, saving or restoring its file. Cancelled older attempts do not post a banner over the newer village. Active simulation updates within the same state remain valid: the current village is protected at application time using the unchanged checkpoint rules.

The method returns `{applied,saved,message}`. A post-restore quota failure accurately returns applied=true/saved=false and keeps the original file warning; protection failure returns applied=false/saved=false. A renderer failure after the actual Game reference changes also reports applied=true/saved=false. This makes partial application visible without falsely promising atomic storage/display rollback. Existing save order, protection requirement, strict decode and autosave invalidation are preserved.
