The exact indexed runtime received32 sequential actual `Game.step(1/30)` calls from the supplied private village, at reduced operating-system priority10, without warmup, a CPU profiler or rendering. Individual step cost remained high: mean137.32ms, median117.40ms, p95196.88ms and maximum570.13ms. There were no simulation errors. Decode was excluded. This short cold resumed-state trace is not a steady-state percentile estimate.

Replaying the same measured cost sequence cyclically for60 modeled drawing opportunities, with explicitly synthetic4ms and12ms drawing overhead, the former unrestricted catch-up loop executed up to3updates per opportunity and averaged397.81ms of simulation work per opportunity (maximum923.44ms). The actual new `advanceFrameSimulation` function executed at most1update for these slow costs, averaging133.63ms (maximum570.13ms). These are scheduling models, not measured frame rates. The new budget improves the chance to draw between updates; it does not make an individual update faster.

Every measured step and modeled callback used exactly1/30. The scheduler discards excess wall-clock debt instead of advancing world time directly or increasing the step size. Contiguous synthetic event counters also pass; this is not exhaustive coverage of all game events. Reduced catch-up can slow simulated time relative to wall time, which is its deliberate tradeoff.

Navigation revision invalidates that cache, and neither the frame budget nor the10ms limit can preempt a synchronous grid rebuild or one slow Game.step. No smooth-gameplay or naval-performance qualification follows from this single sample.

Only aggregate results are public. The private village, names, coordinates, inventories and individual measured cost trace remain outside these reports.
